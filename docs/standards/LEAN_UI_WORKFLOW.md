# Lean UI workflow v1.1

Integrate these conditions into existing Workflow G0–G6 and O11 G0–G6; do not run a second duplicate gate checklist. User authorization, manual merge, checkpoint, baseline validation and truthful evidence remain mandatory where applicable.

## Stage ownership

| Existing gate | Concrete UI outcome | Default executor |
| --- | --- | --- |
| Workflow G0 | Brief, exclusions, selected references, preview behavior vs delivered behavior, route/targets | Primary |
| Workflow G1 / O11 G0-G1 | Read-only O11 foundation → Sites prototype/review → accepted UI contract → bounded O11 plan | Primary; one focused reviewer when useful |
| Workflow/O11 G2-G3 | One native representative slice, targeted readback and validation; affected runtime/fidelity evidence before broad expansion | Primary + independent reviewer at milestone |
| Workflow/O11 G4 | Normal manual Compare and Merge, accepted-live delta | Primary operator |
| Workflow/O11 G5 | Identified publication, required interaction/visual/access checks | Primary or focused QA |
| Workflow/O11 G6 | One current report, actual stage, unresolved work, metrics | Primary |

This adds Sites to new/material UI tasks. Existing O11_ONLY maintenance can reuse an accepted design without generating another Site. Do not silently change an active task's selected route or scope; use a new revision/task when needed. A Sites URL and version/source identity are useful evidence, not proof of O11 feasibility.

## Agent use

Default: one primary operator does intake, design coordination, plan and implementation. Use one independent reviewer for frozen design/native mapping and meaningful implementation changes. Reuse the reviewer thread while identity and revisions remain aligned. QA can be a bounded assignment when execution tools are actually available. Keep existing role definitions; they are optional responsibilities, not required handoffs.

Do not spawn analyst + designer + architect + planner for a fully specified one-screen change merely to produce four overlapping documents. Delegate only if work has a distinct output and useful independence/parallelism. One writer/session owner per O11 module; worker context contains sanitized snapshots and no credentials. Preserve existing runtime subagent permissions.

## Context and evidence

- Keep the root AGENTS entry concise and link to this standard. During integration consolidate duplicated project/workflow sections; retain all operational safeguards.
- One canonical task spec, one UI contract, one plan section and one execution report. Link historical worker outputs instead of copying all of them into every artifact.
- Worker assignment: project/task/revision; outcome; relevant file sections/object IDs; permitted output; evidence subject; concrete checks. Default result: findings/decision/delta/remaining gaps in a short page. Do not limit necessary evidence or truncate errors to satisfy a word cap.
- Save full relevant tool responses once for traceability; use local parsing to extract changed contracts, matching assertions and validation delta. Send compact summaries plus locators to reviewers; reviewers inspect relevant raw evidence for their check.
- Read each changed Screen/Block once per meaningful saved slice; use another read after acceptance/unknown outcome when a different evidence subject must be established. Avoid unchanged seven-object full dumps at every textual correction. If dependencies/shared contracts changed, widen the readback appropriately.
- A deterministic comparator can check repeated structure/value preservation, but its PASS does not prove visual fidelity, business semantics or runtime behavior. No new test framework is required for OML work.
- Reuse completed setup verification unless relevant state changed. No whole-theme/whole-repository rediscovery per worker. Do not send the 800 KB base CSS when a dozen token declarations and three component signatures answer the question.
- No promised token reduction percentage. Record actual usage if the client exposes it; otherwise use null and record artifact/call/rework counts as proxies.

## Scope and fixture control

Keep every required reference state in the acceptance matrix. Place screenshot scenario selection and visual fixtures in Sites or test harness by default; the final O11 UI receives only explicitly required controls and behaviors.

Avoid encoding 12 complete copies of 12 rows with every default/backup field when shared defaults plus scenario deltas express the same cases. Use a typed list/structure with keyed updates when the installed API supports it; verify feasibility once. If a fixed-record implementation is justified, still avoid redundant fixture serialization. Do not rewrite an existing accepted model merely for aesthetic code compactness.

No CRUD does not automatically mean a complete client business simulator. Define which interactions are presentation, local UI state, mock transitions and real operations. A test harness/scenario switcher or approve/reject/reminder state machine is additional delivered behavior only when explicitly selected.

## Model policy

Begin with the user's chosen model/effort. Reduce task ambiguity, context repetition and unnecessary work before increasing effort or adding model tiers. Escalate a specific unresolved diagnosis when evidence justifies it. This package does not pin models or change account/client configuration.
